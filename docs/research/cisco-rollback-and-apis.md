# Rollback primitives and structured read APIs: IOS-XE and NX-OS

Research for [#5](https://github.com/lcleveland/network-mcp/issues/5) (map [#1](https://github.com/lcleveland/network-mcp/issues/1)).
Scope: IOS-XE 17.x and NX-OS 9.3/10.x on Nexus 9000, from Cisco configuration guides and command references.
Every claim cites its page. Lines marked **Unverified** are not stated in a primary source and need a lab check.

## Answer in brief

- **IOS-XE has a real device-side timed auto-revert.** `configure terminal revert timer <1-120>` (Rollback Confirmed Change) and `configure replace <file> time <minutes>` both revert on their own unless `configure confirm` arrives in time. Both need `archive` / `path` configured first.
- **NX-OS has exactly one timed auto-revert: `configure replace <file> commit-timeout <30-3600 s>`**, confirmed with `configure replace commit`. The file must be a complete `show running-config`, not a set of change lines. Checkpoint/rollback and Session Manager have **no timer**, and Session Manager only covers ACL and QoS.
- **Neither platform documents a running-config hash command.** Both document diffs: IOS-XE `show archive config differences`, NX-OS `show diff rollback-patch` and `show diff running-config <file>`. The server should hash a normalized `show running-config` itself.
- **Structured reads:** NX-OS returns JSON over plain SSH (`show ... | json`), so NX-API adds little for reads. IOS-XE has no documented JSON over the CLI. Its structured path is RESTCONF, which needs HTTPS server config and an AAA user at **privilege 15**.

## IOS-XE 17.x

### Primitives

| Primitive | Command | Auto-reverts on a timer? |
|---|---|---|
| Config archive | `archive` / `path <url>` / `maximum <1-14>` (default 10) / `time-period <min>`; `archive config` saves a copy | No. It is the snapshot store the others need. [^xe-cr] |
| Timed `configure terminal` | `configure terminal revert {timer <min> \| idle <min>}` (1-120 min) | **Yes.** It reverts if the change is not confirmed. [^cf-c] |
| Confirmed replace | `configure replace <url> [nolock] [list] [force] [ignorecase] [revert trigger [error] [timer <min>] \| time <min>]` | **Yes** with `time` or `revert trigger timer`. `revert trigger error` reverts on error. [^xe-rcc] [^xe-cr] |
| Confirm | `configure confirm` | It stops the pending revert. It does **not** save to startup. [^cf-c] |
| Adjust or fire | `configure revert {now \| timer {<min> \| idle <min>}}` | `now` reverts at once; `timer` resets the clock. [^cf-c] |
| Exclusive lock | `configure terminal lock` (needs `configuration mode exclusive`, which IOS-XE 3.1S+ replaced with `parser command serializer`) | n/a [^cf-c] |

Key facts:

- The `time minutes` form: "If the `configure confirm` command is not entered within the specified time limit, the configuration replace operation is automatically reversed." [^xe-cr]
- `configure revert` and `configure confirm` need the Configuration Archive enabled first. [^cf-c] [^xe-rcc]
- **Only the user who started the timed rollback can confirm it, reset the timer or cancel it.** [^cf-c]
- During `configure replace` the running config is locked by default (`nolock` turns this off). The lock "is automatically cleared at the end of the configuration replace operation". `show configuration lock` shows current locks. [^xe-cr]
- `configure replace` needs a **complete** config file generated by an IOS device. It computes a diff and applies it in passes, normally three or fewer and never more than five. A failed revert in multi-pass cases "may" leave a partial config. It also needs free memory larger than the two configs combined, or it does not run. [^xe-cr]
- Plain `configure terminal` applies each line immediately; there is no candidate datastore on the CLI. (General IOS behaviour; the revert feature exists because of it.)

### When the SSH session drops

- The revert timer runs on the device, so a dropped session does not stop it. An unconfirmed change reverts when the timer fires. This is the fail-safe behaviour the map's design wants.
- **Unverified:** whether a *new* session from the same user can `configure confirm` after the original vty is gone. The reference ties confirm to "the user who initiated" the rollback [^cf-c], not to the session. If confirm fails in a new session, a dropped SSH session always means a revert. That is safe, but the confirm step must then run on the same connection as the apply, or be retried knowing the change may revert.
- **Unverified (practitioner report, not primary):** a Cisco Community thread reports a timed revert that left a stale configuration lock, which was cleared only by a reload. Reproduce in the lab before relying on revert unattended. `clear configuration lock` exists for "erratic or abnormal behavior". [^cf-c]

### Diff and hash

- `show archive config differences [file1 [file2]]` compares two files line by line; with no arguments it compares running and startup. `show archive config incremental-diffs <file>` lists the lines in a file that are not in the running config. [^xe-diff] [^cf-show]
- No documented running-config hash. `verify /md5 <file>` hashes files; whether it accepts `system:running-config` on IOS-XE 17 is **unverified**.
- **Recommendation:** SHA-256 over `show running-config` after dropping the volatile header lines (`Building configuration...`, `Current configuration : N bytes`, `! Last configuration change at ...`, `! NVRAM config last updated at ...`).

### Structured read: RESTCONF

- Enable with `restconf` plus `ip http secure-server`. The API root is `/restconf`, data lives under `/restconf/data`, and the media types are `application/yang-data+json` and `application/yang-data+xml`. Methods: GET, PATCH, PUT, POST, DELETE, HEAD, OPTIONS. [^xe-restconf]
- **Access requires AAA users at privilege level 15** ("RADIUS or TACACS+ users defined with privilege level 15 access are allowed"). [^xe-restconf] A read-only credential therefore cannot use RESTCONF.
- Operational data lives in `Cisco-IOS-XE-*-oper` models and is on by default. Config lives under `Cisco-IOS-XE-native:native`. [^xe-restconf]
- RESTCONF has no confirmed-commit or rollback; the guide does not mention either. [^xe-restconf] It is not supported on dual-IOSd or software-redundancy setups. [^xe-restconf]
- Turning RESTCONF on is itself management-plane config (`ip http ...`, AAA), which the map's denylist forbids the server to touch. An operator would have to enable it beforehand.

## NX-OS 9.3 / 10.x (Nexus 9000)

### Primitives

| Primitive | Command | Auto-reverts on a timer? |
|---|---|---|
| Checkpoint | `checkpoint [<name>] [description <d>]` / `checkpoint file <url>`; `no checkpoint <name>`; `clear checkpoint database` | No [^nx-rb] |
| Rollback | `rollback running-config {checkpoint <name> \| file <url>} [atomic \| best-effort \| stop-at-first-failure]` (default `atomic`) | **No.** Manual only. [^nx-rb] |
| Config replace | `configure replace <url> [verbose \| show-patch] [best-effort] [commit-timeout <30-3600 s>]`, plus `verify-only` / `verify-and-commit` (9.3(1)+) | **Yes, only with `commit-timeout`.** [^nx-cr] |
| Confirm | `configure replace commit` | It stops the commit timer. [^nx-cr] |
| Session Manager | `configure session <n>` → `verify` → `commit` / `abort` | No timer. On a failed commit it reverts to the original. **ACL and QoS only.** [^nx-sm] |
| NX-API `cli_conf` | request element `rollback`: `stop-on-error` / `continue-on-error` / `rollback-on-error` | No timer. It rolls back within the request on error. [^nx-api6] |

Key facts:

- Commit-timeout: "If you enter the `configure replace commit` command before the timer expires, the commit timer stops." "If the commit timer expires, roll back to the previous configuration is initiated automatically." The timer starts after the replace completes. [^nx-cr]
- **There is no early manual revert:** "To rollback to the previous configuration, you must wait for the expiry of the commit timer." No other configure replace can start while the timer runs. [^nx-cr]
- The replace file "must be the valid show running-configuration output", not a partial config. Configure replace "is always atomic", except `best-effort`, which does **not** restore the previous config on error. [^nx-cr]
- One operator at a time: "Only one user can perform the configuration replace, checkpoint, and rollback operations"; parallel SSH or NX-API sessions doing so are unsupported. Cisco advises against config changes from other sessions during a replace. [^nx-cr]
- Checkpoints: at most 10 user checkpoints, names up to 80 characters, `system-*` names reserved. They survive reload unless `write erase` runs first. An atomic rollback fails if the config changes during it. [^nx-rb]
- Session Manager: up to 32 sessions, not persistent across reload, ACL/QoS only. [^nx-sm] It cannot carry general interface or VLAN changes.
- Status and logs: `show config-replace status` (includes the commit timer and time remaining), `show config-replace log exec`, `show config-replace log verify`, `show checkpoint summary`, `show rollback log`. [^nx-cr] [^nx-rb]

### Getting a timed revert for a change set on NX-OS

There is no `configure terminal revert timer` on NX-OS, and the only timer needs a full target config. Options for the plan/apply flow:

1. **Stage the target on the device.** `checkpoint pre` → apply the lines in `configure terminal` → `copy running-config bootflash:<target>` → `rollback running-config checkpoint pre` → `configure replace bootflash:<target> commit-timeout N` → `configure replace commit`. The timer is real and on the device, but the change is applied, removed and applied again (three disruptions).
2. **Render the full target on the server.** Fetch `show running-config`, merge in the plan, then upload the result and run `configure replace ... commit-timeout`. One disruption, but the server must merge NX-OS config text correctly, which is hard and risky in general.
3. **Checkpoint with a server-driven rollback.** `checkpoint pre` → apply → server waits for confirm → `rollback running-config checkpoint pre`. Simple, but the revert depends on the server staying alive and connected. It is **not** a platform auto-revert.

None of these is as cheap as the IOS-XE path. This matters for the map's "uses platform auto-revert" decision (see below).

### When the SSH session drops

- The commit timer runs on the device. Docs do not say what happens to a running timer when the SSH session that started it drops. Because the replace finishes before the timer starts [^nx-cr], the expected behaviour is that the timer keeps running and reverts. **Unverified:** lab check required.
- **Unverified:** whether `configure replace commit` from a new session (same or different user) stops a timer started by another session. The docs place no per-user restriction on it, unlike IOS-XE.
- A drop *during* a `configure terminal` change leaves whatever lines have already been applied. Nothing reverts them except a later rollback.

### Diff and hash

- `show diff rollback-patch {checkpoint <a> | running-config | startup-config | file <f>} {checkpoint <b> | ...}` shows the patch between any two sources. [^nx-rb] [^nx-showd]
- `show diff running-config <file_url> [unified] [partial] [merged]` and `show diff startup-config <file_url> [unified]` were added in 10.2(3)F ("candidate config integrity check"). With `partial`, they check whether a candidate snippet is present in the running config. [^nx-cand] This is useful for post-apply verification of a plan.
- No documented running-config hash. Use the same method as IOS-XE: SHA-256 over `show running-config` with the `!Command:` / `!Running configuration last done at:` / `!Time:` header lines removed.

### Structured read: JSON over SSH or NX-API

- Any show command that supports it can be piped to `| json` / `| json-pretty` (or `| xml`) on the plain CLI, so **structured reads work over the SSH baseline without NX-API**. [^nx-api6] JSON Native keeps integers as integers. [^nx-api3]
- NX-API itself: `feature nxapi`, `nxapi {http|https} port <p>`, request types `cli_show` / `cli_show_array` / `cli_show_ascii` / `cli_conf` / `bash`, JSON-RPC 2.0 or ins_api format. It allows up to 10 consecutive show commands per request, and its `nxapi_auth` cookie lasts a fixed 600 s. [^nx-api3] [^nx-api6]
- Limits: JSON output above 1 MB comes back as XML; the JSON ceiling is 60 MB; chunked output is XML only; consistency-checker commands support XML only. [^nx-api3] [^nx-api6]
- NX-API is also management-plane config (`feature nxapi`), so it would need an operator to enable it.

## Evaluation against the map's standing decisions

- **"Apply ... uses platform auto-revert"**: met natively on IOS-XE (`configure terminal revert timer`). On NX-OS it is met only by `configure replace ... commit-timeout`, which needs a full-config file (option 1 or 2 above). A checkpoint-only design (option 3) is **not** platform auto-revert. Grilling must pick one or relax the decision for NX-OS.
- **"Apply refused if the running-config hash changed"**: neither OS gives a hash, so the server computes it from a normalized `show running-config`. Normalization rules are per platform and need recorded transcripts.
- **"Explicit confirm"** maps to `configure confirm` (IOS-XE) or `configure replace commit` (NX-OS). The IOS-XE confirm is tied to the user who started the revert. On both platforms, confirm only stops the revert; it does not save. Whether to `copy running-config startup-config` afterwards is a separate decision.
- **"NX-API and RESTCONF optional if research shows they help"**: NX-API adds little because `| json` works over SSH. RESTCONF is the only structured path on IOS-XE, but it needs a privilege 15 credential and operator-enabled HTTPS. That conflicts with the least-privilege read refs. Suggest keeping RESTCONF out of v1, or making it opt-in with that trade-off stated.
- **Concurrency**: NX-OS allows one replace/checkpoint/rollback at a time per device, and IOS-XE locks running config during replace. This supports the "one device per call" rule and needs a per-device write lock in the server.
